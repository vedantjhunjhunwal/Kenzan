# Submission integrity

This page answers four questions:

1. What in this repository was produced by an AI?
2. Where could ground truth and predictions be coupled?
3. Where is the chat log?
4. How was the release archive made?

Written 2026-10-25 from what the repository itself records. Where the repository can't settle a
question, this page says so instead of guessing.

## 1. AI involvement

Kenzan was built with Claude (Anthropic) as a coding and research assistant. Every commit up to and
including PR #1 was originally authored "Claude <noreply@anthropic.com>". On 2026-10-26, at the
repository owner's request, `main` was rewritten so that those commits name the owner as author and
committer, and the `Co-Authored-By: Claude` and `Claude-Session` lines were then removed from the
commit messages. File trees are unchanged. The original commits are kept on the branches
`archive/claude-authored-main` and `archive/claude-authored-pr1`. `release/COMMIT_MAP_rewrite.txt` maps
each original hash (the ones cited in the freeze logs, the release notes and the notebook pin) to its
current hash on `main`. The git history on `main` therefore no longer shows who wrote the code: this
page and the archive branches do. The user directed the work, made the
decisions recorded in `stress/FREEZE_LOG.txt`, ran the Colab notebook, and did the verification steps
marked "user" below. The code, tests, documentation, result files and this page were written by the
AI assistant.

## 3. Shared code that could couple ground truth to predictions

The ground-truth builders import parts of the pipeline they evaluate. A bug in a shared function
would change both sides the same way and stay invisible to the scores.

| Ground-truth code | Imports from `docparse` | Risk |
|---|---|---|
| `gt/build_gt.py` (reference page) | `export.write_all`, `hierarchy.assign_label_paths`, `normalize.label_norm`, `normalize.parse_value`, `normalize.decimals_for`, `validate.run_checks` | label normalisation, label paths, value parsing (△, dashes) and checks are computed by the same code as the predictions |
| `bench/build_gt_xbrl.py` (real filings) | `export.write_all`, `hierarchy.assign_label_paths`, `hierarchy.cluster_1d`, `normalize.label_norm`, `normalize.DASH_GLYPHS`, `router.decide`, `validate.run_checks` | same, plus the router decides which pages are "verifiable"; values come from XBRL text, not from `parse_value` |
| `gt/detection_power.py` | `validate.Cell`, `validate.check_sum` | the detection power of the checks is measured with the checks themselves (it's a property of the window, so this is by design) |
| `gt/synthetic_pages.py` | none (its own NFKC normalisation and paths) | not coupled |
| `docparse/evaluate.py` (scoring) | – | aligns rows by `label_norm`, each side computed by its own builder. With shared `label_norm`, a normalisation bug can make two different labels look equal |

Mitigations in place:

- the reference values were read from pixels, not from the text layer the parser reads;
- the benchmark values come from XBRL, with |fact| = printed × 10^scale checked per cell;
- `score_dimensions` scores values by row position as well as by label, so a label problem can't hide
  a value problem.

What is **not** mitigated: `label_norm` and `label_path` are shared, so label-level scores on the
reference page and the benchmark can't detect a normalisation bug.
